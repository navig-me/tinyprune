# tinyprune-store (in development)

Durable metadata-only SQLite persistence for the unreleased Rust agent. TinyPrune remains a macOS-only product; this crate is not a Linux or Windows release or proof of native platform safety.

## Ownership and integration

`Store::open(path)` opens/creates a database; `Store::memory()` provides isolated in-memory storage. Both default to `PathFlavor::Posix`. Windows hosts must use `Store::open_with_flavor(path, tinyprune_windows::PATH_FLAVOR)` (or `memory_with_flavor` for portable fixtures): containment, root-key lookup, subtree retirement and Trash descendant cleanup normalize Windows prefixes/separators and compare case-insensitively. Stored path hints retain their original spelling; POSIX equality semantics are unchanged. This constructor choice is independent of persisted scheduler settings. The caller owns database-directory creation and permissions. `Store` implements core `PolicyStore`, `ObservationStore`, `AuditSink` and agent `AgentStore`, `AgentAudit`. Never hold a store transaction across filesystem work.

**Connections.** One *writer* connection (mutex) runs every mutation as an IMMEDIATE transaction. A file-backed store also opens a second **read-only WAL connection with its own mutex** that serves every read method (`runtime_state`, `load_snapshot`, candidate/deadline/audit/decision pages, counts, `latest_decision`, reclaim, `database_bytes`, observations), so queries never wait for the writer mutex, an open write transaction, or its fsync; they read the last committed snapshot. In-memory stores cannot be opened twice and share one connection for both roles. Clones are `Send` and share both connections; the mutex coordinates clones, not independently opened handles.

The core `ObservationStore::projects` API returns a borrowed slice, so each handle keeps a project snapshot. Use one handle as the observation/project writer; its `publish_projects`/`remove_below` refresh that snapshot. Call `refresh_projects` after external changes or before transferring observation ownership. Policy, deadlines, observations and audit reads always query SQLite. Policy reads use a single transaction.

Open configures foreign keys, WAL, `synchronous=FULL` and a five-second busy timeout. SQLite in-memory databases use SQLite's memory journal instead of WAL. Forward-only migrations use `PRAGMA user_version`, one transaction per version, reject newer schemas, and preserve previous-version data. This is a distinct Rust schema, **not** an importer of the Swift product database. Versions 1 and 2 cover base repositories and the reclaim ledger respectively. Nonpersistent device-number observations/projects/deadlines are discarded on reopen; explicit overrides and audit history are retained.

Schema version 3 adds durable policy revision, timed pause and activity-retention preferences. `runtime_state` returns `(revision, paused_until, retention_days)`; `replace_policy` replaces rules, roots, overrides and all settings in one audited compare-and-swap transaction. Stale revisions fail without writes. Existing single-repository policy mutations also advance revision. Timed pause expiry and retention execution belong to the daemon, using injected time, not this clock-free store.

Schema version 4 indexes full decision identities and decouples reclaim history from activity-row retention. `latest_decision` retrieves full wire explanations by UUID/resource hex, respecting conflicting creation/generation guards; `AuditRecord::event` decodes core event rows without exposing the private persistence codec. `prune_audit(before)` deletes at most 256 expired activity rows per call, preserves pending attempt records and never deletes lifetime/daily reclaim rows. The daemon chooses the injected-time cutoff; older full explanations are activity and expire with that history.

Retention `0` means "keep forever", matching Swift `AgentSettings` (reference defaults: 0 s grace, hidden protection off, retention 0). `prune_audit` therefore deletes nothing while the stored retention is 0, independent of the cutoff passed in. Fresh databases are deliberately **not** seeded with 30 days/3600 s/hidden-protected: that would contradict the Swift reference, and a migration cannot distinguish an explicit "keep forever" from the default, so none rewrites existing rows.

Schema version 5 adds the **current decision** projection for large-tree overview/upcoming/rule screens: `current_decisions(identity_key PK, root FK→roots ON DELETE CASCADE, scheduled_at NULL, rule_id NULL, preview, payload, updated_at)` with partial indexes `(scheduled_at, identity_key)`, `(rule_id, scheduled_at, identity_key)` and `(preview, scheduled_at, identity_key)` (all `WHERE scheduled_at IS NOT NULL`). `put_decisions(at, &[DecisionRow])` upserts a whole batch in one transaction with cached prepared statements; unchanged rows write nothing, new/changed rows also append the `schedulingDecision`/`previewMatch` audit record. Rows disappear in the same transaction wherever their candidate row does (subtree publication, `remove_below`, `MovedToTrash`, root removal; enforced by trigger + FK cascade). `decision_counts`, `decision_rule_stats`, `decision_page` read only those indexes; a test asserts the query plans use indexes with no temp sort or table scan. `decision_page(rule, preview)` with both filters orders by the rule index and filters `preview` per row. The migration also adds a `candidates.path_hint` column (backfilled from the stored payload) with covering indexes so subtree publication and `remove_below` never decode candidate JSON, and a `deadlines(root)` index.

Publication is diff-based: `publish_candidate_subtree` rewrites only changed rows and returns the number of inserted/changed/deleted rows (0 = identical, no write, no audit); `replace_deadlines` upserts only new/changed rows (and audits only those) and deletes vanished ones, so an identical set writes nothing; `save_observation` skips the write transaction when the committed row already equals the merged result. Each remaining observation write is still its own durable `synchronous=FULL` transaction; the core `ObservationStore` trait offers no batch entry point.

Incremental entry points for the agent: `AgentStore::update_deadlines(root, evaluated, deadlines)` upserts `deadlines` (audit only for new/changed rows) and deletes the deadline of every `evaluated` identity that has none in `deadlines`, touching no other row and never scanning the root; `upsert_candidates(candidates, at)` writes only inserted/changed candidate rows (longest managed root per path, audit `candidatesUpserted` only when something changed) and retires nothing. Neither authorizes Trash.

Windows-flavor containment (`open_with_flavor(.., PathFlavor::Windows)`) computes one `WindowsKey` (normalized, single-scalar-uppercased) per root and per tested path instead of normalizing both operands for every pair; publication, subtree retirement, `remove_below` and Trash descendant cleanup are linear in the rows scanned and keep exactly the previous semantics (differentially tested in `tinyprune-core/tests/windows_path_equivalence.rs`). Identity keys are hex-encoded without per-byte allocation. Ignored benchmark: `cargo test --release --locked -p tinyprune-store --test windows_scale -- --ignored --nocapture` (file-backed, real fsync; Windows-flavor and POSIX-flavor rows at 25k/50k/100k).

Schema version 6 makes `current_decisions` orphan-free by construction: existing orphans are deleted by the migration, `put_decisions` skips (silently, inside its transaction) any row whose candidate row is gone, and a `BEFORE INSERT` trigger aborts any other insert without a candidate. Together with the delete trigger and FK cascade this means a decision computed before a Trash or removal can never resurrect a row for that item.

`rusqlite` with `bundled` closes the concrete platform gap of absent/differing system SQLite installations. The pinned `Cargo.lock` includes SQLite's C build dependency chain. No system SQLite runtime is required, but building bundled SQLite requires a C compiler for the selected target (a Windows SDK/MSVC toolchain on Windows). `serde`/`serde_json` encode versioned database payloads without adding serialization dependencies or I/O to the pure core. Private DTO codecs reconstruct validated rule/matcher models and preserve path bytes, identity guards, Windows flavor, hidden metadata, and optional timestamps.

## Repositories and safety

- Ordered rule and explicit override insert/update/delete, managed-root replacement, global pause/hidden/grace/path-flavor settings. Root validation and canonical filesystem resolution remain the platform/runtime caller's responsibility; storing a root never authorizes Trash.
- Overrides retain stable identity plus mutable path hints, with Inherit, Keep and CustomExpiry policies (the core's explicit expiry representation). No child file is modified. Keep precedence and final identity/policy/protection checks remain the core coordinator's responsibility.
- Identity-keyed observations refresh the persisted hint on every write, retain earliest/latest dates across rename, and reset dates for a conflicting creation/generation identity. Projects preserve activity maxima, replace missing projects only within the published subtree, and refresh hints. `remove_below` retires observation, project and candidate metadata using current path hints in one transaction, so old-path removal after a new-path scan preserves renamed identities.
- Atomic per-root deadlines, deadline-order index `(scheduled_at, identity_key)`, keyset pagination and conditional removal by full identity plus original deadline. Candidate metadata snapshots have identity-keyset pagination. Pages are live keyset views, not frozen snapshots: deleting already-returned rows does not shift remaining rows; newly inserted/retimed rows before the cursor require starting a new traversal. No offset scans.
- `publish_candidate_subtree` atomically replaces only a completed scan's subtree, maps items to the longest matching managed root and clears vanished items for an empty scan. `candidate_count`, ascending row-id `audit_page`, and descending bounded `audit_recent` avoid unbounded client overview reads.
- `database_bytes` reports SQLite `page_count × page_size` for the persistent database pages only (excluding WAL/SHM files and filesystem allocation). It reads database metadata, never user-file contents.
- Config import parses with core `ConfigDocument`, derives Preview rules with core `document_rules`, and atomically replaces roots/rules/exceptions. Export uses core `config::render`. The supported config subset round-trips canonically; the core renderer honestly comments about nonrepresentable policies. Settings, active state and identity-bound overrides are not encoded in that config format.
- State mutations and their audit records commit together. Trash attempts and their pending marker commit together. Success closes the marker, conditionally removes the same identity's deadline, removes its candidate metadata and same-volume descendant candidates, and appends the success and reclaim ledger row in one transaction; failure closes the marker and records failure, retaining retry scheduling. A filesystem move cannot be part of a SQLite transaction: a move followed by database failure remains an interrupted attempt with unknown outcome, not fabricated success.
- `dangling_attempts` and `finish_recovery` implement the engine's startup recovery contract. `Agent` invokes them before indexing/cleanup. Other hosts must call `reconcile_attempts(injected_now)` before scheduling/execution. Recovery atomically closes each attempt and records an unknown-outcome safety skip; it is idempotent and never counts an unknown attempt as reclaimed. Opening alone does not invent a clock or silently recover.
- Reclaim totals and UTC daily buckets derive exclusively from committed success ledger rows. Bytes are moved-to-Trash bytes, **not** free disk space; unknown sizes contribute zero bytes and zero known-size items. Migration backfills prior success audit rows. Daily ranges are half-open and days with no moves are omitted.

`AgentStore::replace_deadlines` receives only identity/source/scheduled time, not a complete scan decision or occurrence clock. Its transactional `deadlineScheduled`/`deadlineRemoved` records use that scheduled time. The daemon's batched `put_decisions` stores the full explanation in the current projection and one compact audit row per changed decision in the same FULL transaction. `record_decision(at, preview, full_explanation_json)` remains the standalone full-history API; its transaction is not atomic with an earlier deadline publication. Runtime IPC must still return full explanations, never treat a persisted deadline as deletion permission. Core audit events for preflight Preview, safety skips, attempts, success and failure are stored by `AuditSink`.

The Swift persistence boundary also includes a versioned override metadata codec/reconciliation role. **Platform adapter TODO (out of this crate's scope):** xattr/Windows ADS override export/reconciliation. SQLite is the authority here; no xattrs/ADS or inherited child metadata are written.

## Decision write diagnostics and schema 8

`put_decisions` reuses cached lookup/upsert/audit statements across rows and batches. Every inserted/changed decision still has its own audit record in the same `synchronous=FULL` transaction; identical and missing-candidate rows append nothing. The full explanation is stored once in `current_decisions`, not duplicated into every scheduling audit payload. Compact scheduling/preview payloads have `version: 1`, `identityKey`, `item` (volume/resource/path hint/creation/generation/persistence), identity guards, `scheduledAt`, `ruleID` and `preview`. They are activity metadata, **not** full Explanation DTOs; consumers must not deserialize them as full explanations.

Schema 8 archives the final full explanation in an audit record before a current decision is deleted, in the same transaction, including candidate cleanup and root cascades. This preserves full explanation lookup for moved/removed activity without duplicating each intermediate explanation. `latest_decision` returns current full explanations or archived/legacy full audit rows, never compact rows; identity guards still apply. Intermediate historical compact activity does not reconstruct a historical full explanation. Archive rows use the last decision's `updated_at`, not an invented removal clock. Archive insertion failure rolls back removal. Retention applies to these full archives just as to other activity.

Schema 8 also drops `candidate_path` and `observation_path`: since schema 7, subtree predicates use the normalized `path_key` indexes, not `path_hint`. Root/FK-cleanup indexes and all schedule/rule/preview/audit indexes remain; they serve distinct queries.

Set `TINYPRUNE_PHASE_LOG` to append JSONL records for `store.decisions.begin`, `store.decisions.sql` and `store.decisions.commit`. Begin includes writer-lock/IMMEDIATE-transaction acquisition; SQL includes validation, encoding, comparisons, statement stepping and index work; commit isolates SQLite commit (including any automatic checkpoint). Each reports input `items`, `changed_rows`, changed full `payload_bytes`, compact `audit_bytes`, elapsed `ms` and wall-clock `end_ms`. No paths, identities, rule IDs or payload contents are logged. Successful batches emit after commit; failed batches emit no successful phase records. An unset/unopenable sink is inert. The diagnostic sink is best effort, not an audit authority; its writes never relax SQLite durability.

Each phase's `end_ms` is captured when that phase actually finishes, before deferred emission, so the SQL timeline is not shifted by commit latency. Failed transactions discard captured timings rather than publishing success records.

Standalone raw SQLite diagnostic matrix (from `rust/`):

```sh
cargo test --release --locked -p tinyprune-store --test bench -- --ignored --nocapture
```

The ignored `raw_sqlite_100k_matrix` test prints a Markdown table and appends it to `TINYPRUNE_BENCH_OUT` when set, for release CI artifacts. It crosses FULL/NORMAL/OFF with WAL/fresh-default journal, production decision/audit secondary indexes versus PK-only, and full-duplicate versus compact audit payloads: 24 cases, each 100k synthetic rows in 25 transactions of up to 4,096 rows (final batch: 1,696), matching runtime decision page sizing. It reports SQL versus commit timing, row counts, total and per-row payload/audit bytes, and database/WAL bytes. This isolates SQLite/index/payload costs, not native Windows traversal or end-to-end runtime safety; timings are observations only when actually run. NORMAL/OFF are benchmark controls only; production policy, audit, scheduling and Trash storage remain FULL.

Local release measurements (100k synthetic rows, all secondary indexes, 25 commits; individual runs, not statistical comparisons):

| Host | FULL/WAL audit payload | SQL | COMMIT including auto-checkpoint | Database bytes |
|---|---|---:|---:|---:|
| Development Mac | full duplicate | 1.930 s | 5.386 s | 311,869,440 |
| Development Mac | compact | 1.559 s | 4.003 s | 215,445,504 |
| Docker Linux/aarch64 | full duplicate | 1.470 s | 3.555 s | 311,869,440 |

The synthetic full explanation averages 1,107.889 bytes/row; compact audit averages 340.889 bytes/row instead of another 1,107.889 bytes. These are fixture sizes, not a claim about every real explanation. COMMIT includes SQLite auto-checkpoint work and does not isolate a kernel `fsync` syscall. NORMAL/OFF did not uniformly improve these local runs; no production durability setting or decision page size was changed based on them.

Windows Server 2022 diagnostic run 39535868984 (`a65a430`) isolated the runtime bottleneck as COMMIT/checkpoint, not SQL: 100,101 decision rows in 25 batches took 8.80 s in the SQL phase and 188.63 s in COMMIT (longest 13.98 s), 197.43 s total. The raw synthetic FULL/WAL/indexed control took SQL 1.265 s + COMMIT 14.038 s with duplicated audit, versus SQL 1.100 s + COMMIT 9.301 s with compact audit. FULL/default-delete/indexed controls were 2.410 s + 8.796 s (duplicate) and 2.462 s + 9.524 s (compact); NORMAL/WAL/indexed was 1.218 s + 13.860 s (duplicate) and 1.219 s + 10.760 s (compact). OFF/WAL/indexed COMMIT was 0.785 s (duplicate) and 0.916 s (compact). The runtime-to-raw gap is not explained by these controls; no antivirus/storage-driver or individual fsync attribution is claimed.

The additional ignored `cargo test --release --locked -p tinyprune-store --lib bench_put_decisions_checkpoint_and_readers -- --ignored --nocapture` exercises the real Store schema/API after preloading 100k candidates and deadlines. It compares default 1,000-frame autocheckpoint with and without IPC-like upcoming reads, then 0 and 10,000-frame controls with readers. Durability stays FULL/WAL throughout. Deterministically shuffled schedule keys exercise index writes unlike the raw matrix's constant deadline. Each case reports total `put_decisions` time, final checkpoint time and WAL bytes; final TRUNCATE happens only after readers stop. These are isolated benchmark controls, not production configuration changes.

## Verification

From `rust/`:

```sh
cargo test --locked -p tinyprune-store
cargo clippy --locked -p tinyprune-store --all-targets -- -D warnings
cargo check --locked -p tinyprune-store --target x86_64-unknown-linux-gnu --all-targets
cargo check --locked -p tinyprune-store --target x86_64-pc-windows-msvc --all-targets
```

Tests exercise empty/previous/newer schemas, temp-file WAL/foreign keys/reopen, all repositories, config canonical round-trip, rollback on audit/ledger failure, interrupted-attempt recovery and rollback, deadline/candidate keyset pagination, identity-hint refresh across rename/restart, replacement identity guards, reclaim totals/days, and an engine run with scripted time and injected metadata/Trash. No sleeps, child content reads or real user Trash.

On the development macOS host, native tests and Clippy ran successfully. The two cross-target commands were attempted but cannot compile bundled SQLite without C cross-toolchains: Linux lacked `x86_64-linux-gnu-gcc`; MSVC lacked Windows target standard headers (`stdlib.h`). Installing Rust targets alone is insufficient. These are not successful cross-target checks; native target CI/toolchains must execute them.
