# ADR 0011: Rust runtime: store, scan, ipc, daemon, cli, UI

Status: Accepted as in-development engineering direction. Nothing here is released; no Linux or Windows build exists. TinyPrune remains a macOS-only product whose shipping implementation is Swift. This ADR extends [ADR 0010](0010-cross-platform-core-and-golden-fixtures.md) and does not change `spec.md`.

## Context

ADR 0010 produced a pure Rust decision core, a synchronous agent engine and three platform adapters (`tinyprune-unix`, `tinyprune-watch`, `tinyprune-windows`), but no durable state, production enumerator, process, protocol, command line or UI. Embedding those pieces is the work that turns the engine into something that can be run and evaluated. Every product invariant still applies: Trash only, metadata only, Keep wins, the store schedules but never authorizes, Preview never trashes, and the core coordinator re-checks identity, policy and protection immediately before every move.

## Decisions

1. **Crates.** Add `tinyprune-store` (SQLite persistence), `tinyprune-scan` (bounded metadata traversal and read-only Preview dry run), `tinyprune-ipc` (protocol, transports, shared endpoint resolution), `tinyprune-daemon` (the `tinyprune-agentd` binary) and `tinyprune-cli` (the `tinyprune` binary) to the main workspace. The UI is not a member of it (decision 5).
2. **`rusqlite` with `bundled`.** System SQLite is absent or differs across Windows, Linux distributions and macOS releases. Bundling closes that concrete gap at the cost of requiring a C compiler for the target (MSVC on Windows) and preventing `cargo check --target` cross-checks from a host without C cross-toolchains. The store uses forward-only `PRAGMA user_version` migrations, WAL and `synchronous=FULL`. Its schema is distinct from the Swift product database; it is not an importer or migrator for it.
3. **IPC: length-prefixed JSON, no Swift wire compatibility.** Frames are a four-byte big-endian length plus UTF-8 JSON, over a Unix domain socket (mode 0600, peer uid verified) or a Windows named pipe (protected DACL, peer SID verified). A handshake negotiates a protocol version that starts at 1, independent of Swift XPC's version 3. DTOs follow the concepts of the Swift IPC types but are not XPC- or Codable-compatible; golden DTO samples live in `Fixtures/ipc/dtos.json`. The macOS app, Finder extension and Swift CLI keep using XPC. Dependencies are `serde`/`serde_json`, `libc` for Unix peer credentials, and the locked `windows` bindings for named pipes.
4. **`ctrlc` dependency.** The daemon needs a portable Ctrl-C/SIGINT handler that `std` does not provide; `ctrlc` is a small crate for that single gap. SIGTERM is not handled.
5. **Tauri UI in a separate workspace.** `rust/ui` has its own `Cargo.toml`/`Cargo.lock` and is excluded from `rust/Cargo.toml`, so webview/GTK dependencies cannot break the core workspace or its CI. The frontend is build-step-free HTML/CSS/vanilla JS with Node's built-in test runner. It is only an IPC client (`agent_request` via `tinyprune-ipc::Client`); it evaluates no rules and trashes nothing, and saving a rule always creates or edits it in Preview.
6. **macOS stays on Swift.** The Rust daemon, CLI and UI do not replace the Swift app, agent, Finder extension or Sparkle updater, and Rust is not shipped to macOS users. Rust runs on macOS only as a development and regression host.
7. **Config codec is POSIX-only.** The core config text codec is the Swift-reference POSIX contract. On a Windows-flavor agent, config import and export return `InvalidRequest` rather than parse Windows paths with a POSIX codec. A Windows config codec is a later, separate decision.
8. **Reconcile fallback where no native watcher is wired.** Linux uses inotify and Windows uses `ReadDirectoryChangesW`. macOS has no native Rust watcher (no FSEvents or kqueue), so the daemon rescans each managed root on a periodic bounded reconcile (default 300 seconds, injectable). Rescan signals from native watchers also trigger reconcile and watcher recreation. This is a documented fallback and a latency compromise, not an FSEvents replacement.
9. **Identity and race limits are inherited, not fully solved.** POSIX `rename` and Windows Shell deletion cannot atomically condition a move on source identity; identity is checked immediately before and after, and a post-move mismatch is reported without deletion or unsafe rollback. Identity is restart-stable only when it is built from a durable volume id (macOS volume UUID via `getattrlist`; Linux filesystem UUID from mount information, mixed with the mount root; Windows volume serial) plus inode or 128-bit file ID and creation time. Otherwise (tmpfs, overlayfs, FUSE, network filesystems without a UUID, no creation time) the identity is marked non-persistent and the store discards its schedules on reopen, so a restart re-observes those items and restarts their FirstObserved clocks; a conflicting creation time resets dates rather than reusing them. Cloned volumes sharing an id are not distinguished. The persistence tests ran on the macOS development host only; the Linux path was never executed and Windows was compile-checked only. Watcher paths and scan results are hints and never authorization.

## Consequences

- One reviewed policy path: every IPC mutation passes through the core's validation and the store's compare-and-swap revision check; stale revisions fail without writes. A transport failure after a mutation leaves the outcome unknown and clients never auto-retry.
- The daemon serializes IPC mutations and ticks behind one agent mutex. Scheduling is deterministic under an injected clock; tests drive ticks without sleeps.
- `tinyprune-ipc` endpoint defaults are shared by daemon, CLI and UI: `TINYPRUNE_ENDPOINT`, then `TINYPRUNE_SOCKET`, then the per-OS default.
- Shipping any of this to Linux or Windows would additionally require native verification, installers, accessibility review and a spec amendment, none of which exist.

## Status and verification (honest limits)

Observed (crate READMEs and a run during documentation): on the macOS development host the new crates' native tests and Clippy are reported passing by their READMEs; `tinyprune-scan` traversed 50,101 entries at 35,761 entries/sec in its ignored release benchmark (2026-10-20, Darwin x86_64); the UI's 9 Node frontend tests pass (`node --test tests/*.test.js`, observed 9 of 9). The shared golden contract has 577 cases. The pushed head before these crates (6672a10) passed `rust-core` CI on `ubuntu-24.04`, `windows-2022` and `macos-14`; the new crates are not yet in a pushed CI run.

Not verified: real inotify events; the Windows `ReadDirectoryChangesW` watcher; Windows named pipes; Linux and Windows execution of the store, scan, IPC server, daemon and CLI; the Tauri shell on Linux or Windows (a real webview and screen reader were never run); installers and packaging (unsigned development archive scripts and the `rust-artifacts.yml` workflow exist but were never run on Linux/systemd, Windows or GitHub); performance on Linux or Windows; any accessibility audit beyond static HTML/CSS contract tests and computed contrast. An end-to-end smoke, a non-gating benchmark and a `rust-ui` job are configured in `ci.yml` but had not run on GitHub when this was written. The per-component matrix is in [rust/README.md](../rust/README.md#status-matrix).
